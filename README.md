# Cedarline Community Credit Union

## Local setup

1. Create a Neon PostgreSQL project and copy its pooled connection string, including `sslmode=require`.
2. In Vercel Project Settings > Environment Variables, add `DATABASE_URL` (the Neon pooled URL with `sslmode=require`) and `ADMIN_MASTER_PASSWORD`. Assign both to each Vercel environment you use. The app reads runtime environment variables and does not load `.env` files.
3. Install dependencies with `npm install`.
4. Start the local Vite app and temporary API with `npm run dev:stack`, then open `http://localhost:5173`.

This is a fictional banking demonstration. Account/routing values, balances, cards, generated history, requests, and receipts are simulated and cannot be used for real banking or payments. No payment network is contacted. Admin-created accounts can be individual, business, or joint; generated account numbers use numeric formatting, and generated routing numbers are intentionally invalid for bank validation.

The Vite React Router app serves `/`, `/trading`, `/platforms`, `/features`, `/pricing`, `/login`, `/signup`, `/dashboard`, `/profile`, `/transactions`, `/market-data`, and `/admin`. API routes use the `/api/auth/*`, `/api/admin/*`, and `/api/transactions` families. `npm run dev:stack` uses Neon when `DATABASE_URL` is configured server-side; it falls back to in-memory preview data only when no database URL is set.

Numbered SQL migrations in `migrations/` are applied automatically on the first API request after `DATABASE_URL` is configured. Migrations `004`–`011` add joint accounts, unique transaction IDs, request destinations, admin audit records, opening-funding labels, persisted member address fields, and normalize existing opening-balance history and dates without changing balances. Neon Postgres persists members, accounts, integer-cent balances, ledger entries, requests, payment instructions, and admin changes. User passwords are bcrypt-hashed; session and admin routes are authorization-protected.

## Vercel deployment

1. Import this repository into Vercel and deploy it as a Node.js project.
2. In **Project Settings → Environment Variables**, configure these server-side variables for every environment that needs access:
   - `DATABASE_URL`: Neon pooled PostgreSQL connection string with SSL required.
   - `ADMIN_MASTER_PASSWORD`: the single administrator master password. Do not add it to source, HTML, or `NEXT_PUBLIC_*` variables.
   - `APP_URL`: the canonical HTTPS deployment URL.
3. Redeploy after setting or changing environment variables. On first use, the server reads `DATABASE_URL` and applies each unapplied numbered SQL migration transactionally before serving API requests. No separate migration command is required.
4. Visit `/admin` to manage users, balances, requests, and payment settings. Sign-up and sign-in are available at `/signup` and `/login`.

Admin and customer API routes verify server-side sessions, accepting an HTTP-only cookie or an opaque Bearer session token. The master password remains server-side and is not stored in the database. Passwords are stored as bcrypt hashes. This deployment remains a fictional demo and does not initiate or represent real financial transfers.

## Dates, balances, and ledger

Account opening dates are stored in the existing `accounts.created_at` field; admins can select a non-future date when creating an account, and that saved date is shown to the member. Transaction timestamps are generated by PostgreSQL. Balances and transaction arithmetic use integer cents. A new signup starts with fictional demo funding; this is not a real money transfer. An admin-created opening balance is stored as one opening-balance ledger entry; no synthetic past activity is created. Add Funds instructions are configured by an admin and shown to members. When a member confirms a deposit or withdrawal in the demo review flow, the server validates and atomically updates the fictional balance, request, and ledger, then returns a unique transaction ID. A withdrawal receipt is displayed only after that commit succeeds. These local demo transactions do not contact or represent a real bank or payment network. Admin actions are persisted to the audit history.

The migration supports imported ledger rows with both `imported = true` and a required `source_date`. No historic records are imported by this project. The old `data/users.json` and `data/midwest.db` are demo-era local data and are intentionally not represented as verified Neon account or transaction history.

## Tests

Run `npm test`. The integration tests use an in-memory PostgreSQL-compatible database and cover admin authorization, signup/login/verification, user CRUD, balances and ledger synchronization, payment instructions, confirmed demo transactions, and withdrawal receipts.
